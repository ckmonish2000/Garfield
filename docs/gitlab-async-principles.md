# GitLab Async Communication Principles

## Overview

GitLab, as a fully remote company with 2,000+ team members across 65+ countries, has built one of the most comprehensive frameworks for asynchronous communication. Their approach is documented in their public handbook (2,700+ pages) and serves as the gold standard for remote-first organizations.

**Source**: [GitLab Handbook - Asynchronous Communication](https://handbook.gitlab.com/handbook/company/culture/all-remote/asynchronous/)

---

## Core Philosophy

### Handbook-First Principle

> "The handbook is the single source of truth"

- **Documentation over meetings**: Information is written down first, discussed second
- **Public by default**: 99% of handbook is publicly accessible (including to competitors)
- **Always current**: Updated via merge requests with clear ownership
- **Searchable knowledge**: "Look it up in the handbook" before asking colleagues

### Benefits
- Reduces interruptions and dependency on real-time responses
- Preserves context across time zones and team changes
- Enables new team members to onboard independently
- Creates institutional memory that survives turnover

## Key Principles

### 1. Async by Default

**Meeting Philosophy**:
- Meetings are optional by default
- Detailed agendas required for all meetings
- Live Doc Meetings format: collaborative documentation during sync time
- Recording and documentation for those who can't attend

**Communication Norms**:
- Slack/chat without pressure for immediate reply
- Clear response time expectations (24-48 hours typical)
- Non-linear workday support (work when you're most productive)

### 2. Public by Default

**Transparency Rules**:
- All information accessible unless specifically private
- Clear reasoning when something must be private
- Internal discussions happen in public channels
- Decision rationale documented, not just decisions

**Impact**:
- Eliminates "reply all" culture
- Prevents information silos
- Builds trust through radical transparency
- Enables contribution from unexpected sources

### 3. Written Communication First

**Documentation Standards**:
- Write things down before synchronous discussion
- Clear project scope and requirements in writing
- Decisions documented with context and alternatives considered
- Templates and processes that are replicable

**Quality Over Speed**:
- Take time to write clear, comprehensive documentation
- Edit for clarity and completeness
- Link to related context and decisions
- Use structured formats (markdown, templates)

## Practical Implementation

### Meeting Best Practices

**Before the Meeting**:
- Create agenda in a shared doc (Google Docs, GitLab issue)
- Share agenda 24+ hours in advance
- Attendees add questions/topics asynchronously
- Mark items as "async-resolvable" vs "needs discussion"

**During the Meeting**:
- Use Live Doc format: everyone edits the same document
- Document decisions and action items in real-time
- Capture dissenting opinions and alternatives discussed
- Assign clear owners for follow-ups

**After the Meeting**:
- Share recording and transcript
- Clean up notes for clarity
- Update handbook with any new decisions/processes
- Close async-resolvable items without meeting needed

### Communication Tools

**Primary Channels**:
- **GitLab Issues/MRs**: Project work, code reviews, feature discussions
- **Handbook**: Processes, policies, company knowledge
- **Slack**: Quick questions, social, urgent coordination
- **Zoom**: Synchronous meetings (when truly needed)
- **Google Docs**: Collaborative document creation

**Tool Selection**:
- Persistent topics → Handbook or GitLab issues
- Ephemeral coordination → Slack
- Complex collaboration → Live Doc meetings
- Quick sync → Brief video calls (recorded)

### Async Workflows

**Decision Making**:
1. Create proposal in handbook or GitLab issue
2. Share with stakeholders (@ mentions)
3. Set clear deadline for feedback (e.g., 72 hours)
4. Address feedback asynchronously via comments
5. Document final decision with rationale
6. Update handbook with new process

**Project Collaboration**:
1. Define scope and requirements in writing
2. Break work into discrete issues with clear acceptance criteria
3. Async reviews via merge requests with detailed comments
4. Update progress in issues (status, blockers, questions)
5. Use labels and milestones for visibility
6. Summarize weekly progress in written updates

**Knowledge Sharing**:
1. Default to handbook updates over presentations
2. Record demos/presentations for async viewing
3. Write blog posts or internal docs for major learnings
4. Create templates for repeatable processes
5. Link related documentation for context

## Cultural Norms

### Response Time Expectations

**Urgent (< 4 hours)**:
- Production incidents
- Security issues
- Customer escalations
- Explicitly marked as urgent with context

**Normal (24-48 hours)**:
- Slack messages
- Email
- Review requests
- Questions in issues

**Low Priority (72+ hours)**:
- Non-blocking feedback requests
- Nice-to-have improvements
- General discussions

### Writing Guidelines

**Be Explicit**:
- State assumptions clearly
- Define acronyms on first use
- Link to context (don't assume shared knowledge)
- Specify timezone for time-sensitive items

**Be Complete**:
- Provide enough context to understand without asking
- Include relevant links and references
- Anticipate questions and address preemptively
- Use screenshots, videos, or diagrams where helpful

**Be Considerate**:
- Respect different working hours (no expectation of immediate response)
- Use threading to keep conversations organized
- Tag people only when their input is needed
- Mark items as FYI vs Action Required

## Common Challenges & Solutions

### Challenge: "Too much writing overhead"
**Solution**:
- Writing actually saves time (one doc vs. many explanations)
- Templates reduce creation time
- Good documentation prevents repeated questions

### Challenge: "Lack of human connection"
**Solution**:
- Dedicated informal communication channels
- Coffee chats (video calls without agenda)
- Virtual team events
- Async social interactions (watercooler channels)

### Challenge: "Slow decision making"
**Solution**:
- Clear deadlines for feedback
- DRI (Directly Responsible Individual) model
- Escalation paths when blocked
- Distinguish between reversible and irreversible decisions

### Challenge: "Important context in Slack gets lost"
**Solution**:
- Move important Slack discussions to issues/handbook
- Slack for ephemeral, handbook for persistent
- Regular handbook updates from learnings
- Search-first culture

## Key Metrics

GitLab measures async effectiveness:
- **Handbook merge requests**: Frequency of documentation updates
- **Meeting efficiency**: Ratio of attendees to meeting time
- **Response times**: Actual vs expected for different priorities
- **Onboarding time**: How quickly new hires become productive (proxy for documentation quality)

---

## Lessons Learned

### What Works
- Radical transparency builds trust
- Writing forces clarity of thought
- Async enables thoughtful, not reactive, responses
- Documentation compounds in value over time

### What Doesn't Work
- Making everything async (some things need real-time discussion)
- Passive-aggressive "it's in the handbook" responses
- Documentation without maintenance (becomes outdated/misleading)
- Assuming everyone reads everything (need good search and navigation)
